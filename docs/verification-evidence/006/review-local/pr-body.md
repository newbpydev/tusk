## Post-Deploy Monitoring & Validation

Owner: the release maintainer; a named individual has not been assigned. Validation window: the fresh accepted main candidate through draft/download readback, publication and anonymous install/landing-page readback.

Use `make verify-candidate` with the accepted run/source/version/manifest; inspect retained run/attempt/job, artifact-expiry and signature receipts. Every native/minimum/build/provenance job and subject must match the same accepted source. Complete native terminal/cask gates, retain all 84 CLI and 78 TUI case-runs and packaged startup samples, and require the documented reference tail guards before draft authorization.

Use `make release-readback` with the exact accepted candidate and receipts. Expect all nine public asset names and downloaded SHA256 values to match, the tag to resolve to accepted source, and the release identity/notes to match. Inspect anonymous install/data-preservation behavior on each advertised target, live cask routes, license detection and actual GitHub links/badges/About/topics/social preview before activating claims.

An identity/hash/signature mismatch, expired artifact, incomplete native/performance gate, conflicting tag or changed build input stops prepublication work. Preserve diagnostics and obtain fresh readback/candidate acceptance before retrying. After publication, unintended data loss or wrong executable/installation behavior requires deprecating that version and preparing a new version; never replace public assets or move its tag. A partial tap or metadata failure is reconciled independently and leaves its route/claim pending.
